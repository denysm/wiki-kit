## How to run here

- **Clone**: `git clone --depth 1 --branch v3.10.0 https://github.com/NeoLabHQ/context-engineering-kit $EXTERNAL/context-engineering-kit`, read-only. Read `plugins/<plugin>/skills/<skill>/SKILL.md`; ignore the copies in the root `skills/`, `agents/` and `antigravity/`.
- **Licence**: GPL-3.0. Reading is fine; no text of any part may be copied into the kit, which is MIT. A technique can be carried only in the kit's own words.
- **Telemetry and outbound calls**: none found in the kaizen skills (plain text) or in the reflexion hook (`hooks/src/*.ts` import only `fs`, `readline`, `node:fs/promises` and `os`). Other plugins reach out by design, per their READMEs: git and review use the GitHub CLI `gh`; mcp sets up third-party MCP servers (Context7, Serena, a Paper Search server through Docker MCP) and a CLI.
- **Hooks to avoid**: the only hook, in reflexion, runs on every `UserPromptSubmit` and `Stop` once the plugin is installed and `bun` is on PATH (see its part below).
- **Auto-loading to avoid**: the `kaizen` skill describes itself as "Always applied for" code, architecture, process and error-handling work, and the kaizen README calls it "Automatically applied"; ddd and tech-stack rules load by file pattern once installed.
- **What breaks without the plugin**: the kaizen skills read as plain method text from the clone; nothing in them needs the plugin. Elsewhere, references such as `sadd:judge`, `sdd:researcher` and `/reflexion:reflect` resolve only in an installed plugin; the hook needs `${CLAUDE_PLUGIN_ROOT}`; rule files do not load by pattern.
- **Install**: not needed and not done. Installing the marketplace or any plugin waits for the user's yes.

## Parts read: the kaizen plugin (`plugins/kaizen/`)

Manifest: "kaizen", version "3.0.0", description "Introduces commands for analysis of root cause of issues and problems, including 5 Whys, Cause and Effect Analysis, and other techniques." README: "Continuous improvement framework inspired by the Toyota Production System". Seven skills, all `SKILL.md`; the README lists six as commands and one as a skill.

### `why` (`plugins/kaizen/skills/why/SKILL.md`)

- Description: "Iterative Five Whys root cause analysis drilling from symptoms to fundamentals". State the problem, ask why repeatedly (default depth 5), validate by working back from root cause to symptom, branch when several causes appear, propose solutions for root causes. Notes: "The magic isn't in exactly 5 whys"; "If "human error" appears, keep digging".
- Needs: nothing. Plain text; reads the same from the clone.
- Status: method taken. Five whys is in the kit's own words in `specialists/development-coach/references/methods.md` ("Five whys: a barrier that repeats") and named in `specialists/decision-analyst/SKILL.md`.

### `plan-do-check-act` (`plugins/kaizen/skills/plan-do-check-act/SKILL.md`)

- Description: "Iterative PDCA cycle for systematic experimentation and continuous improvement". Plan (baseline, root cause, hypothesis "If we change X, Y will improve", measurable success criteria), Do (small scale, record deviations), Check (against baseline), Act (standardise, adjust or start a new cycle). "If stuck after 3 cycles, revisit root cause analysis".
- Needs: nothing.
- Status: method taken. PDCA is in the kit's own words in `specialists/development-coach/references/methods.md` and named in `specialists/decision-analyst/SKILL.md`.

### `analyse-problem` (`plugins/kaizen/skills/analyse-problem/SKILL.md`)

- Description: "Comprehensive A3 one-page problem analysis with root cause and action plan". Seven boxes: Background, Current Condition, Goal/Target, Root Cause Analysis, Countermeasures, Implementation Plan, Follow-up; two long worked examples. "Overkill for: small bugs, one-line fixes, trivial issues".
- Needs: nothing.
- Status: method taken. A3 is in the kit's own words in `specialists/development-coach/references/methods.md` ("A3: a case on one page").

### `cause-and-effect` (`plugins/kaizen/skills/cause-and-effect/SKILL.md`)

- Description: "Systematic Fishbone analysis exploring problem causes across six categories". Categories: People, Process, Technology, Environment, Methods, Materials; ask why under each, separate contributing from root causes, prioritise. Three worked examples.
- Needs: nothing.
- Status: candidate.

### `root-cause-tracing` (`plugins/kaizen/skills/root-cause-tracing/SKILL.md`)

- Description: "Use when errors occur deep in execution and you need to trace back to find the original trigger". Trace backward through the call chain to the original trigger, add stack-trace instrumentation when tracing by hand fails, fix at the source, then add validation at each layer.
- Notable: its text and worked example largely match `skills/systematic-debugging/root-cause-tracing.md` of obra/superpowers (MIT; a `diff` of the two bodies, frontmatter left out, gives 46 lines of difference on a file of about 180 lines). It refers to a bisection script `find-polluter.sh` that is not in the kaizen folder (superpowers ships it beside its file).
- Needs: nothing to read; the script it names has to come from elsewhere.
- Status: candidate.

### `analyse` (`plugins/kaizen/skills/analyse/SKILL.md`)

- Description: "Auto-selects best Kaizen method (Gemba Walk, Value Stream, or Muda) for target". Gemba walk (state assumptions, read the actual code, list surprises and gaps), value stream mapping (stages, wait time, efficiency, future state), Muda (seven wastes applied to software: overproduction, waiting, transportation, over-processing, inventory, motion, defects). Long worked examples.
- Needs: nothing.
- Status: candidate.

### `kaizen` (`plugins/kaizen/skills/kaizen/SKILL.md`)

- Description starts "Use when Code implementation and refactoring, architecturing or designing systems, process and workflow improvements, error handling and validation." Four pillars with TypeScript good/bad examples: continuous improvement (smallest viable change, leave code better), poka-yoke (make invalid states unrepresentable, validate at boundaries, fail fast), standardized work (follow existing patterns), just-in-time (YAGNI, "Wait for 3+ similar cases (Rule of Three)", profile before optimising). Ends with red flags and how the five commands fit.
- Notable: "Always applied for" code, architecture, process and error-handling work, so installed it would trigger on most coding requests.
- Needs: nothing when read from the clone; it is then not auto-applied.
- Status: candidate.

## Part read: the reflexion hook (`plugins/reflexion/hooks/`)

- `hooks.json` registers `Stop` and `UserPromptSubmit` with an empty matcher, each running `command -v bun >/dev/null 2>&1 && bun ${CLAUDE_PLUGIN_ROOT}/hooks/src/index.ts <event> || true`; without `bun` it silently does nothing.
- `UserPromptSubmit` saves the session's events, prompts included, as JSON under the system temp folder (`session.ts`: `path.join(tmpdir(), 'claude-hooks-sessions')`).
- `Stop` (`onStopHandler.ts`): when the last user prompt contains the word "reflect" (not as a `/reflect` or `:reflect` command), it blocks the stop with "You MUST use Skill tool to execute the command /reflexion:reflect", so the agent runs one more turn.
- No network call found in `hooks/src/`. The reflexion README: "In order to use this hook, need to have `bun` installed. But for overall command it is not required."
- Needs: the plugin installed (`${CLAUDE_PLUGIN_ROOT}`), `bun`, and the reflexion `reflect` skill under its plugin name.
- Status: candidate.
